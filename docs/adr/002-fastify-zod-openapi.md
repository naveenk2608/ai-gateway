# ADR 002: Fastify with Zod schemas, OpenAPI generated from the schemas

- Status: accepted
- Date: 2026-10-20
- Milestone: M1

## Context

The gateway exposes an OpenAI-compatible API, so request validation has to be exact and the
documentation has to match what is actually enforced. Config is already validated with Zod, and
the HTTP layer sits on the hot path of every request.

## Decision

Fastify 5 with `fastify-type-provider-zod`. Each route declares Zod schemas for its body and
responses; the same schemas drive validation, TypeScript types for handlers, response
serialization and the OpenAPI 3.1 document generated by `@fastify/swagger`. The spec is served at
`/docs/json` and the Swagger UI at `/docs`.

## Alternatives considered

- Express with hand-written validation and docs: the docs drift from the code.
- JSON Schema with Ajv (or TypeBox): fast, but a second schema language next to the Zod config
  schemas.
- NestJS: decorators and a DI container for an API with a handful of routes.

## Consequences

- Unknown fields are rejected, so a client sending an unsupported OpenAI parameter (tools,
  `response_format`, images, `n > 1`) gets a 400 naming the field instead of a silently different
  result. Supporting a new parameter means adding it to the schema, which also documents it.
- Validation errors become OpenAI-style 400s with `param` set to the offending path.
- Response schemas are checked when serializing, so a bug in the gateway shows up as a 500, not a
  malformed body sent to a client.
- Streaming responses (`text/event-stream`) bypass serialization; the route's description
  documents the SSE format.
- Routes are registered in plugins after Swagger so every route appears in the spec.
